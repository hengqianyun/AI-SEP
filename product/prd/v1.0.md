## 1. 背景与问题

### 1.1 背景

团队希望用多 Agent 辅助软件交付，但常见做法存在系统性缺陷：

- 单会话「换帽子」扮演多角色，审查与开发未隔离，结论不可审计；
- 进度依赖聊天上下文，会话关闭即丢失权威状态；
- 规范、技术栈、门禁与具体项目耦合不清，难以复制到新项目；
- 失败经验直接写进全局规则，污染知识库；
- 规划未达成共识即编码，并行任务写冲突无法证明安全。

### 1.2 要解决的问题

1. 如何把「分析 → 规划共识 → 可并行任务 → 开发/审查对抗 → 测试 → 发布」变成**可恢复、可审计**的流水线？  
2. 如何让同一套架构成为**项目模板**，由产品/前后端/测试分工补齐个性化规范后即可实例化？  
3. 如何保证人类在范围、风险与发布上拥有**最终决策权**，Agent 不得伪造共识？

### 1.3 产品定位

AI-SEP 不是「一个全能编码机器人」，而是：

> **工具中立的多 Agent 软件交付操作系统（规范 + 模板 + 控制面）**  
> 可映射到 Cursor、Claude Code、Codex 等运行时；业务差异通过 Rule / Skill / Policy 注入，而非重写角色契约。

## 2. 目标与成功标准

### 2.1 V1.0 目标

| 目标 | 说明 |
|---|---|
| G1 可追踪交付 | 任一 P0 需求可追踪到设计/任务/代码/审查/测试证据 |
| G2 规划门禁 | 必需规划角色未全员明确批准前，不得进入开发 |
| G3 对抗与测试硬门禁 | developer ≠ codeReviewer；P0/P1 与必需测试未清零不得 `VERIFIED` |
| G4 状态可恢复 | 新会话仅凭落盘 Run 状态恢复，不以聊天为权威源 |
| G5 可实例化模板 | 新项目按定制清单与分工表补齐 Org/Project 规范即可启动试点 |

### 2.2 成功标准（验收）

对齐 [`design.md` §17](../../design.md) 的可裁剪子集（V1.0 必达）：

| ID | 标准 | 优先级 |
|---|---|---|
| S-01 | 存在完整 Agent 角色契约与规划/编码/测试决策枚举 | P0 |
| S-02 | 存在 Rule 分层、Skill 模板、workflow policies/definition | P0 |
| S-03 | 存在人类 Owner 与升级路由，共识失败进入 `ESCALATED` | P0 |
| S-04 | 定制清单 + 分工计划可指导一次真实项目实例化 | P0 |
| S-05 | 至少一条试点路径：PRD → 需求快照 → 计划评审一轮（可人工门禁） | P0 |
| S-06 | Run 状态目录约定与 start/resume 协议可执行（允许先半自动） | P1 |
| S-07 | CLI / Cursor Adapter 稳定入口 | P2（可后置） |
| S-08 | Learning 晋升闭环（评分→审批→回滚） | P2（可后置） |

### 2.3 非目标（Out of Scope · V1.0）

- 不绑定单一大模型供应商或单一 IDE 为唯一运行时  
- 不提供托管 SaaS 控制台 / 多人在线编排 UI（V1 以仓库内文件协议为主）  
- 不自动将单次失败晋升为 Global/Org Rule  
- 不替代人类做业务范围、剩余风险接受、最终发布批准  
- 不内置具体业务系统（商城等）实现；业务 PRD 属于**使用本模板的下游项目**  
- 不在 V1 承诺全自动无人值守从 PRD 到生产发布

## 3. 用户与场景

### 3.1 用户角色

| 角色 | 诉求 |
|---|---|
| 产品人员 | 写清范围与领域规则；在冲突时做业务裁决；不陷入提示词工程 |
| 前端 / 后端开发 | 把栈约定、目录边界、命令写进 Skill/Rule；接受任务包边界内实现 |
| 测试人员 | 定义可执行测试门禁与证据格式；环境阻塞不得被记为通过 |
| Tech Lead / Maintainer | 合并规范、裁剪工作流、发布放行、超限升级处理 |
| 平台维护者 | 维护 Global 底线与角色契约，保证模板可复制 |

### 3.2 核心场景

| 场景 | 参与方 | 期望结果 |
|---|---|---|
| UC-01 实例化新项目 | 协调人 + 产品/前后端/测试 | 按分工填完定制项，`status: active` |
| UC-02 从 PRD 启动交付 Run | 用户 ↔ Orchestrator | 创建 `runId`，进入需求分析节点 |
| UC-03 规划委员会共识 | 多角色 subagent + 人类升级 | 全员批准或 `ESCALATED`，无伪造 APPROVE |
| UC-04 并行任务开发 | developer / reviewer / tester | 读写集无冲突；审查与测试硬门禁 |
| UC-05 跨会话恢复 | 任意新主会话 | 读 `state.yaml` 报告下一动作 |
| UC-06 规范演进 | 失败 memory → 候选 → 人工审批 | 分层发布且可回滚 |

## 4. 产品范围（V1.0 功能需求）

需求 ID 格式：`REQ-SEP-{NNN}`。模块码 `SEP` = 平台本体。

### 4.1 协作协议与角色

| ID | 优先级 | 需求摘要 | 验收要点 |
|---|---|---|---|
| REQ-SEP-001 | P0 | 提供工具中立的多角色 Agent 契约（编排、规划委员会、开发对抗、专项审查、人类身份） | `ai/agents/` 角色齐全；职责/禁止/升级方式明确 |
| REQ-SEP-002 | P0 | Agent 仅通过版本化制品交接，不依赖隐含聊天上下文作为权威 | 协议与 start/resume 文档明确；Run 状态落盘约定存在 |
| REQ-SEP-003 | P0 | 同一任务 developer 与 codeReviewer 强制不同实例 | 契约与 Global 规则禁止兼任 |
| REQ-SEP-004 | P0 | 规划评审决策仅允许 APPROVE / REQUEST_CHANGES / BLOCK / ABSTAIN | Schema + 角色文档一致 |

### 4.2 知识分层与个性化

| ID | 优先级 | 需求摘要 | 验收要点 |
|---|---|---|---|
| REQ-SEP-010 | P0 | Rule 分 Global / Organization / Project；不可覆盖安全规则可标记 | `ai/rules/**` + README 优先级说明 |
| REQ-SEP-011 | P0 | Skill 承载技术栈「怎么做」，与角色契约分离 | `ai/skills/**` 模板；定制清单指向 P0 Skill |
| REQ-SEP-012 | P0 | 提供项目定制勾选清单与跨职能任务分配计划 | `PROJECT-CUSTOMIZATION*.md` |
| REQ-SEP-013 | P1 | context-map 支持按角色/路径最小装载规则与技能 | `context-map.yaml` 可填写并有说明 |

### 4.3 工作流与门禁

| ID | 优先级 | 需求摘要 | 验收要点 |
|---|---|---|---|
| REQ-SEP-020 | P0 | 工作流节点与策略可配置（角色启用、轮次、发布审批、升级路由） | `definition.yaml` + `policies.yaml` |
| REQ-SEP-021 | P0 | 规划未全员批准不得进入开发（允许 V1 先人工执行门禁） | 策略与设计文档一致；试点可演示阻断 |
| REQ-SEP-022 | P0 | P0/P1 审查问题与必需测试为完成硬门禁 | 编码对抗与测试章节 + tester Skill 字段 |
| REQ-SEP-023 | P1 | 风险标签触发 security / migration reviewer | `policies.riskTriggers` |
| REQ-SEP-024 | P1 | 并行任务基于 DAG/读写集；束完成后集成审查 | parallel/integration Skill + 设计 §8 |

### 4.4 制品、追踪与控制面

| ID | 优先级 | 需求摘要 | 验收要点 |
|---|---|---|---|

### 4.5 学习与治理（可后置）

## 5. 非功能需求

| ID | 类别 | 要求 |
|---|---|---|
| NFR-001 | 可审计 | 关键状态变更可追加到事件日志；禁止改写历史事件 |
| NFR-002 | 可恢复 | 关闭聊天后，新会话可根据 Run 状态给出下一动作 |
| NFR-003 | 安全 | Global 禁止密钥入库与输出；安全规则默认不可被 Project 削弱 |
| NFR-004 | 可移植 | 业务规则不写死在单一 Adapter；先文件协议后工具映射 |
| NFR-005 | 可裁剪 | UX/API/Security 等规划角色可省略但必须记录原因 |
| NFR-006 | 人机边界 | `ESCALATED` 必须落到具名人类身份，不得由 Orchestrator 代为专业批准 |

## 7. 依赖与约束

- **上游**：`design.md` 为架构真理源；本 PRD 描述「产品要交付什么」，冲突时先修 PRD 或提 ADR。  
- **实例化**：下游业务项目（如商城试点）使用本模板，其业务 PRD 放在该业务仓库的 `product/prd/`，**不**并入本 PRD 范围。  
- **人力**：Org/Project 规范须按 [`PROJECT-CUSTOMIZATION-ASSIGNMENTS.md`](../../PROJECT-CUSTOMIZATION-ASSIGNMENTS.md) 由产品/前后端/测试编写，平台不替代领域知识。  
- **运行时**：V1.0 允许「主会话 Orchestrator + 手动/半自动派发 subagent」；全自动调度器非阻断项。

## 10. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 只写架构不填 Org/Project 规范 | Agent 行为空洞或互相矛盾 | 定制清单 §0 完成判定；分工表强制署名 |
| Orchestrator 越权代批 | 失去制衡 | Global 共识规则 + 角色禁止事项 |
| 模板与业务 PRD 混写 | 范围失控 | 本 PRD 明确排除具体业务系统 |
| 过早全自动调度 | 状态机未稳导致重复派发 | V1 允许半自动；租约/幂等进入 M3 |
