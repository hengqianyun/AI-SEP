## P-01

**Product Owner 信息**

交付位置：`ai/rules/project/owners.yaml` 的 `productOwner`。

```yaml
productOwner:
  name: <姓名或团队名称>
  contact: <可用联系渠道>
  escalationContact: <升级联系人或渠道>
```

完成检查：
- [ ] `name` 与 `contact` 非空且可联系
- [ ] 责任主体与实际需求批准人一致
- [ ] 升级路径已由项目协调人确认

## P-02

**术语表**

交付位置：`product/glossary.md`。

```markdown
# <产品或领域名称>术语表

| 术语 | 定义 | 边界/不包含 | 易混淆术语 | 示例 | 维护人 |
|---|---|---|---|---|---|
| <术语> | <唯一、可判断的定义> | <不属于该术语的情况> | <术语及差异> | <业务示例> | <角色/人员> |

## 待确认术语
- <术语>：<争议点>；确认人：<角色>；期限：<日期>
```

完成检查：
- [ ] 核心实体、参与者、状态和关键动作已有一版定义
- [ ] 易混淆词明确写出差异，而非互相循环引用
- [ ] 与 PRD、模块名称及领域规则用词一致

## P-03

**领域不变量与业务规则**

交付位置：`RULE-PROJECT-DOMAIN.md` 与 `product/business-rules/*`。

```markdown
## 领域不变量

### <INV-ID> <不变量名称>
- 约束：<任何情况下必须成立的业务事实>
- 适用范围：<实体/流程/状态>
- 违反后果：<为何属于 P0，或实际严重级别>
- 检查证据：<可观察字段、事件或验收方式>
- 例外：<无；或批准条件与记录位置>
- Owner：<业务责任角色>

## 业务规则

### <BR-ID> <规则名称>
- 触发条件：<何时应用>
- 输入/前置状态：<条件>
- 规则：<明确、可判定的处理>
- 输出/状态变化：<结果>
- 优先级/冲突顺序：<与其他规则冲突时如何处理>
- 例外与审批：<无；或审批角色及证据>
- 来源：<政策、合同、业务决策或访谈记录>
- 关联不变量：<INV-ID 或 N/A>
```

完成检查：
- [ ] 每条规则和不变量都有稳定 ID
- [ ] 至少明确列出“违反即 P0”的不变量，或说明不存在及确认人
- [ ] 条件、结果、例外可由非开发人员判断
- [ ] 术语与 P-02 一致，冲突已有决策记录

## P-04

**MODULE 业务含义**

交付位置：`modules.yaml` 中各模块的 `code`、`name`、`ownerRole`；路径可留给开发补充。

```yaml
modules:
  - code: <稳定模块代码>
    name: <与术语表一致的业务名称>
    ownerRole: <负责该业务边界的角色>
    businessPurpose: <若 schema 支持，填写一句话职责；否则作为评审备注>
    paths: []
```

完成检查：
- [ ] `code` 唯一、稳定且不含临时编号
- [ ] `name` 与术语表、PRD 用词一致
- [ ] `ownerRole` 能对业务边界作决定
- [ ] 相邻模块的职责重叠已记录并交由协调人处理

## P-05

**规划角色裁剪（业务侧）**

交付位置：`policies.yaml` 的 `optionalRoles.uxUiPlanner`。

```yaml
optionalRoles:
  uxUiPlanner:
    enabled: <true|false>
    omitReason: <启用时填 N/A；禁用时说明项目为何无 UI/UX 规划需求>
    decidedBy: <产品批准角色>
    decidedAt: <YYYY-MM-DD>
    revisitWhen: <重新评估的触发条件或 N/A>
```

完成检查：
- [ ] `enabled` 是明确布尔值
- [ ] 无 UI 时已设为 `false`，并填写可审计的 `omitReason`
- [ ] 启用时已确认 P-06 的责任人
- [ ] 决策和重评条件已由 Product Owner 确认

## P-06

**UX/体验 Skill（条件任务）**

交付位置：`ai/skills/ux-ui-planner/SKILL.md`。仅在 P-05 启用 UX 时填写；禁用时记录 `N/A` 和 P-05 决策引用。

```markdown
## 体验输入
- 设计系统/规范路径：`<路径；暂无则写“暂无，使用文字稿”>`
- 设计稿或文字稿入口：`<路径/受控链接/产出约定>`
- 目标用户与关键场景来源：`<PRD 章节或研究材料>`
- 品牌与内容约束：`<规则路径或 N/A>`

## 体验交付要求
- 必须描述的页面/流程状态：<加载、空、错误、成功等适用状态>
- 交互与反馈要求：<任务所需最低内容>
- 可访问性目标：<项目批准的要求或待确认负责人>
- 响应式/终端范围：<业务要求，不指定实现技术>
- 交接证据：<标注、流程、文案、验收说明的落盘位置>

## 冲突与缺口
- 与业务规则冲突时：<升级角色和记录位置>
- 无设计系统时：<文字稿的最低字段和批准人>
```

完成检查：
- [ ] 设计系统路径或“暂无、使用文字稿”已明确
- [ ] 关键状态、内容和交接证据可被规划角色直接使用
- [ ] 内容不代替前端团队选择组件或实现技术
- [ ] 与 P-05、P-07 及前端技术侧补充无冲突

## P-07

**试点 PRD 与非目标**

交付位置：`product/prd/`。

```markdown
# <PRD-ID> <需求名称>

## 元信息
- Owner：<产品责任人>
- 状态：<草案/评审中/已批准>
- 优先级：<项目采用的优先级及理由>
- 目标版本/时间窗：<值或待确认日期>

## 问题与目标
- 用户/业务问题：<当前问题及证据>
- 目标：<可验证结果>
- 成功指标：<指标、基线、目标值、观察周期>

## 范围
- In Scope：<本次必须交付的能力>
- Out of Scope：<明确不做的能力及原因>
- 受影响角色/流程：<范围>

## 需求
### <REQ-ID> <需求标题>
- 场景：<谁在什么条件下做什么>
- 验收标准：
  - [ ] <可观察、可判定的结果>
- 关联规则：<BR-ID/INV-ID>
- 优先级：<值>

## 依赖与风险
- 依赖：<团队、系统、决策或 N/A>
- 风险：<风险、影响、Owner>

## 开放问题
- <问题>；Owner：<角色>；截止：<日期>；阻塞：<是/否>
```

完成检查：
- [ ] 范围、优先级、Out of Scope 和开放问题完整
- [ ] 每条需求有 ID 和可判定验收标准
- [ ] 领域规则引用正确，不擅自改变已批准不变量
- [ ] 试点规模足以走通流程且未夹带无关目标

## P-08

**需求快照模板试填**

交付位置：`ai/schemas/templates/requirement-snapshot.md` 的样例，或首份 `SNAP`。

```markdown
# <SNAP-ID> 需求快照

- 来源 PRD：<PRD-ID/路径/版本>
- 快照时间：<YYYY-MM-DD>
- Product Owner：<角色/人员>
- 范围摘要：<本快照覆盖内容>
- 明确非目标：<Out of Scope>

## 冻结需求
| REQ-ID | 需求摘要 | 优先级 | 验收标准引用 | 业务规则 | 状态 |
|---|---|---|---|---|---|
| <REQ-ID> | <一句话> | <值> | <PRD 章节/内联标准> | <BR/INV-ID> | <已确认/待确认> |

## 约束与依赖
- 约束：<业务、合规、时间或 N/A>
- 依赖：<依赖及 Owner>

## 未决项
- <问题>；Owner：<角色>；解除条件：<条件>

## 变更控制
- 快照后允许变更者：<批准角色>
- 变更记录位置：<路径>
- 越权判定：<哪些变化必须退回 Product Owner>
```

完成检查：
- [ ] 已使用 P-07 的真实或演示内容完整试填一次
- [ ] 产品分析角色无需猜测即可映射范围、REQ、验收和非目标
- [ ] 未决项与已冻结内容清楚分离
- [ ] 变更批准角色和越权边界明确

## P-09

**既有产品向设计决策（条件任务）**

交付位置：`design/decisions/`。存在既有决策时逐条记录；不存在时填写 N/A 记录。

```markdown
# <DEC-ID> <决策标题>

- 状态：<提议/已批准/已废弃>
- 日期：<YYYY-MM-DD>
- 决策 Owner：<业务批准角色>
- 关联需求/规则：<PRD-ID、REQ-ID、BR-ID 或 N/A>

## 背景
<需要固化的产品约束、冲突或历史原因>

## 决策
<已选择的产品方向及适用边界>

## 未选择方案
- <方案>：<未采用原因>

## 影响
- 用户/业务影响：<影响>
- 后续约束：<规划和实现不得改变的内容>
- 重评触发：<何时允许重新决策>
```

无既有决策时：

```markdown
# P-09 既有产品向设计决策检查
- 结果：N/A
- 原因：<为何当前没有需迁移或固化的既有决策>
- 确认人：<Product Owner>
- 确认日期：<YYYY-MM-DD>
- 重评触发：<出现何种情况时重新检查>
```

完成检查：
- [ ] 每条决策使用稳定、唯一的决策 ID
- [ ] 决策、边界、影响和重评触发可被后续角色执行
- [ ] 无决策时已留下 N/A、原因、确认人和日期
