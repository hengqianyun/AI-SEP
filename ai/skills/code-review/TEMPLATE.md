# Code Review Skill 填写模板

> Code Review 负责人复制本结构填写 `SKILL.md`。尖括号内容必须替换；不适用项写 `N/A` 及原因。  
> 本 Skill 只写“怎么审查”；技术选型与版本边界应引用 Organization / Project Rule。  
> 前端与后端检查项合并在同一文件中，按变更路径选用对应段落。  
> 已填写示例：[`EXAMPLE.md`](./EXAMPLE.md)（仅展示粒度，不代表默认技术栈）。

## 1. 元数据

```yaml
---
id: skill.code-review
version: 1.0.0
status: draft
owner: <审查负责人或 Tech Lead>
inputSchema: task-package@1
outputSchema: code-review@1
compatibleRoles: [codeReviewer]
appliesTo:
  paths:
    - <适用路径 glob，例如 **/*>
relatedRules:
  - RULE-ORG-CODING
  - RULE-PROJECT-ARCHITECTURE
  - <其他适用 Rule ID>
---
```

- `owner` 应是可批准本 Skill 的角色/团队。
- 前端、后端检查项可共用本 Skill；`paths` 覆盖实际审查范围。
- `relatedRules` 只引用已存在且适用的 Rule ID。

## 2. 适用范围与前置条件

```markdown
## 适用范围

- 审查对象：`<前端 / 后端 / 全栈路径说明>`
- 输出模板：`ai/schemas/templates/code-review.md`
- 技术栈约定引用：`<前端 Skill / 后端 Skill / Rule ID>`
- 命令工作目录：`<仓库根目录或子目录>`

## 前置条件

- 已装载任务包、REQ、冻结契约与适用 Rule/Skill
- 开发者输出中含验证命令与实际结果（含 BLOCKED）
- 禁止在审查意见中粘贴真实密钥或生产数据
```

## 3. 审查工作流

```markdown
## 审查工作流

1. 读取任务包、`allowModify`、REQ 与变更摘要。
2. 按变更路径选用前端检查项、后端检查项或两者。
3. 对照适用 Rule/Skill 与验证证据，区分阻塞问题与建议。
4. 使用规定输出模板记录结论；P0/P1 清零前不得批准。
5. 跨模块、架构或产品范围争议升级，不自行扩权裁决。
```

## 4. 通用必查清单

```markdown
## 通用必查

- [ ] 正确性：满足任务目标与关联 REQ
- [ ] 范围：未越出 `allowModify`，未偷扩需求
- [ ] 架构：未违反 RULE-PROJECT-ARCHITECTURE 与不可破坏约定
- [ ] 安全：密钥、注入、鉴权、数据暴露已按风险规则检查
- [ ] 契约：API/数据与批准版本一致
- [ ] 测试：必要层级已执行；失败或未执行项未被描述为通过
- [ ] 提交卫生：无构建产物、调试垃圾、真实环境文件或无关格式化
```

## 5. 前端审查检查项

```markdown
## 前端审查检查项

### 必查
- [ ] 变更位于允许写路径，未越过共享边界
- [ ] 组件、状态、路由和数据访问遵循适用 Rule/Skill
- [ ] 用户可见状态与验收标准一致（loading/empty/error/success 等）
- [ ] 鉴权、输入处理、敏感数据和依赖变化已按风险规则检查
- [ ] 适用前端验证命令已执行，证据完整
- [ ] 未绕过统一 API Client、Design Token 或鉴权机制

### 阻塞规则
- 必须阻塞：`<功能错误、安全/隐私风险、契约破坏、缺失强制证据等>`
- 升级而非自行裁决：`<跨模块、架构或产品范围争议>`

### 不得仅以风格阻塞
- 已由自动格式化/Lint 覆盖且检查通过的个人偏好
- 未写入项目规则、无用户影响且不造成维护风险的主观写法
- 仅有替代偏好时，标记为非阻塞建议并说明收益
```

无前端交付时：本节写 `N/A` 及豁免依据。

```markdown
## 后端审查检查项

| 检查项 | 阻塞条件 | 证据 | 明确不作为阻塞的纯风格项 |
|---|---|---|---|
| 写边界与模块职责 | `<越权路径、违规依赖>` | `<diff / 路径>` | `<命名偏好等>` |
| API/错误/日志约定 | `<破坏契约、错误结构、敏感日志>` | `<契约 diff / 日志样例>` | `<措辞偏好>` |
| 数据访问与迁移 | `<未评审迁移、破坏兼容、缺回滚>` | `<迁移文件 / 评审记录>` | `<N/A>` |
| 鉴权与数据暴露 | `<越权、明文密钥、过度暴露>` | `<测试 / 配置路径>` | `<N/A>` |
| 验证证据 | `<强制命令未跑或伪称 PASSED>` | `<命令结果>` | `<额外建议性检查>` |
| `<其他项目项>` | `<可判定条件>` | `<命令/测试/路径>` | `<待填/N/A>` |

### 阻塞规则
- 必须阻塞：`<正确性失败、安全红线、契约破坏、缺失强制证据>`
- 升级：`<架构边界争议、共享契约冲突、安全剩余风险>`
```

无后端交付时：本节写 `N/A` 及豁免依据。

## 7. 输出与批准

```markdown
## 输出格式

- 使用：`ai/schemas/templates/code-review.md`
- 结论：`<APPROVE / REQUEST_CHANGES / BLOCK>`
- P0/P1：`<列表；清零前不得批准>`
- 非阻塞建议：`<列表>`
- 升级事项：`<无，或事项 + Owner>`

## 批准门禁

- P0/P1 未清零 → 不得 `APPROVE`
- 环境 `BLOCKED` 未被误记为通过 → 否则 `REQUEST_CHANGES` 或 `BLOCK`
- 纯风格项不得升为 P0/P1，除非已写入适用 Rule
```

## 8. 激活检查

- [ ] 阻塞与非阻塞边界可被客观判定
- [ ] Tech Lead 确认与 Rule/架构无冲突
- [ ] `context-map.yaml` 已按需装载本 Skill
- [ ] Owner 将 `status` 改为 `active`
